# WhatsApp linking — INACTIVE backend foundation

**Review only. Do not merge, deploy, expose as an endpoint, connect an account, or use real user data.** No WhatsApp integration, code generation, chat access, authentication, network listener, SQL, browser changes, or production configuration is included. Nothing here makes PR #5's disabled UI operational. The static GitHub Pages app has no continuously running backend.

## What this proves (and does not)

`unavailable.cjs` is a transport-neutral 503/no-store placeholder and is not wired into any server. It intentionally does not inspect a request, perform authentication, or handle requests. `owner-state.cjs` is a small in-memory prototype of owner-scoped, bounded, expiring pending-state bookkeeping. It holds only a session UUID, supplied principal UUID and expiry; it accepts and emits no phone, pairing code, token, or chat. One pending item per owner, five-minute TTL, random IDs, owner-scoped lookup/cancel, and indistinguishable missing/other-owner lookup are implemented. It is synchronous and process-local, not a distributed store. Expiration is enforced on access, not by a background timer. The owner UUID is **not authenticated**: format validation is not identity verification. The injected test dependencies are not a security boundary. This store must not be exposed directly or used as production authorization. `pending` does not mean a connection is running.

Run offline: `node --test whatsapp-link-foundation/owner-state.test.cjs`.

## Production gates, all unresolved

1. Resolve the current Rada public chat-file exposure and independently validate RLS, storage policies, realtime subscriptions, historical public links, and two-user isolation on staging. The inactive client privacy patch in PR #6 is not a fix. Do not send sensitive files while exposure remains.
2. User decision and risk review on unofficial personal-account linking: it can violate platform terms or cause account restriction; official WhatsApp Business features and coexistence have different capabilities and may not provide arbitrary personal chat access. Confirm a maintained integration and its current terms; do not assume support.
3. A dedicated, continuously running backend/worker (GitHub Pages cannot do this), isolated staging, TLS, restricted ingress, security updates, resource limits, monitoring without sensitive logging, and clear operational ownership.
4. Implement server-side verification of Supabase JWT signature, issuer, audience, expiry, and revocation/session policy using trusted keys; derive the owner only from verified claims, never from body, query or client-supplied user ID. Deny by default. Every session, chat operation and realtime event must be scoped server-side to that owner; validate independently with multiple accounts/devices. UUID validation here is not verification.
5. Before any code flow, design authenticated, short-lived, rate-limited, CSRF/origin-protected endpoints; no codes or credentials in URLs, logs, analytics, browser storage, service workers, or caches. Show transient codes in memory only, with expiry, cancellation, and single use; never ask the user to paste them into chat. Avoid copying secrets to client state, and use no-store responses and restrictive CORS/security headers. Reauthentication and anti-abuse controls require design.
6. Personal-account session credentials require encrypted server-side storage using a managed secret/key service, strict per-owner access and rotation, no secrets in source/logs, auditable unlink/revocation/deletion, account-consent UX, retention limits, and incident response. A stable, shared atomic store is required for multiple workers; the prototype's in-memory state loses everything on restart and cannot coordinate workers.
7. Design a private, minimal chat sync and access layer, isolating per-user data across sockets, background jobs and storage. Include reconnect, unlink, cleanup, retries, rate limits, platform disconnects and privacy-preserving telemetry. No message or credential data should be persisted in browser storage; current Rada behavior must be audited, not assumed safe.
8. Threat-model and obtain security review; add authenticated integration and adversarial tests (forged/expired JWTs, IDOR, cross-user sockets, CSRF, replay, rate limits, cache leakage, multiple workers, revocation, crash recovery, and deletion), staged end-to-end consent and live tests only after explicit approval, with rollout and rollback plans.

The lab state module is only an aid for reasoning about a narrow authorization invariant. Passing offline tests does not establish production security or prove actual WhatsApp functionality.
