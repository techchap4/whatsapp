# Privacy: INACTIVE, incomplete proposal and required server audit

**INACTIVE / INCOMPLETE — DO NOT MERGE OR DEPLOY.** `app-privacy-INACTIVE.patch` contains proposed `app.js` and `extras.js` changes; it has NOT been applied to this branch. No security fixes in this proposal are live. The tests describe the patched local files and are not representative of the remote branch until the patch is applied. Backend permissions, realtime/storage authorization, and end-to-end behavior remain unverified. End-to-end encryption is not implemented by this proposal.

The proposed patch changes only the client, not Supabase or previously deployed clients. It is not a security boundary: a modified client can bypass display settings and query filters. No live backend configuration, policies, content, or objects were inspected or changed. These are code observations, not a finding that any particular bucket or table is public.

## Proposed client behavior and trade-offs — INACTIVE until patch applied

- **Proposed, INACTIVE:** `messages` reads would be limited to the signed-in user as sender or receiver, and realtime message subscriptions would be similarly filtered. The patched client would reject unrelated events as defense in depth; server RLS and realtime authorization remain essential.
- **Proposed, INACTIVE:** With read receipts off, the patched client would not send new `messages.read` updates. It would clear unread indicators in memory only; these may return on reload or on another device. When the setting is turned on, opening a chat may send receipts for previously unread messages. Previously sent receipts cannot be retracted. A stale or older client, another device, or direct API calls can behave differently; concurrent in-flight updates may already have been sent. This is not server-side enforcement. If the local profile is missing, the patched client would not send a read update.
- **Current limitation (not fixed by proposal):** Photo, about, and online controls are display preferences only. `profiles` are loaded with `select('*')`, presence is tracked in a shared channel, and `last_seen` is written to profiles. Hiding them in the UI does not prevent access through an API, realtime, storage URL, or another client. Blocks likewise need server authorization.
- **Proposed, INACTIVE:** New verification requests would be paused in the patched client because the privacy of `verification-docs` and associated request policies is unknown. Existing badges and requests would not be deleted. Older clients or direct API calls can still upload if the server permits them; the pause does not protect existing documents. Do not upload IDs until server access is reviewed.
- **Current limitation (not fixed by proposal):** The app obtains public-form URLs for `chat-media`, `chat-files`, `group-files`, `statuses`, and `avatars`. Actual accessibility depends on bucket configuration and policies; links can be accessible to anyone when buckets are public. Group and direct-message attachments require separate authorization. Do not assume a long URL is private.
- **Current limitation (not fixed by proposal):** No end-to-end encryption is implemented here. Message content is sent to the service. Avoid sensitive chats and documents until protections are verified.

## Backend audit plan (requires authorized Supabase project access)

Review configuration and metadata only initially; do not browse user messages, download IDs, share credentials, or perform intrusive tests. Use a nonproduction clone with synthetic users/objects for behavioral tests. Record the actual schema and configuration before planning changes; no schema or existing policy is assumed here.

1. Identify the project and inventory tables, columns, views, policies, role grants, realtime publication/authorization, triggers and RPC/function definitions, including security-definer functions and their privileges. Compare to app usage: `messages`, `profiles`, `statuses`, `status_views`, `blocks`, `verification_requests`, `reports`, and the `rada_group_*` tables, plus admin RPCs. Check RLS is enabled and effective for exposed roles, views and RPCs, including update/delete/insert as well as select, and ensure no privileged key is shipped to the browser. The browser's anon/publishable key is not an authorization boundary.
2. In staging, with distinct synthetic accounts A, B, C and an anonymous session, verify direct-message reads and realtime events are restricted to sender/receiver; recipients can only make intended receipt changes; sender identity cannot be spoofed; and C/anonymous cannot read or alter A/B data, including via broad queries, updates, views, RPCs or realtime. Test cross-user profile/settings and last-seen visibility, status/views, blocks, and group membership/message/invite/request access. Test admin-only actions against ordinary users, including self-promotion through profile updates or RPCs. Confirm any privacy preferences are actually enforced by a trusted server design; the current UI alone is insufficient.
3. Inspect bucket visibility and storage-object policies for `verification-docs`, `chat-media`, `chat-files`, `group-files`, `statuses`, and `avatars`, as well as any actual bucket names discovered in the project. In staging, use synthetic files to verify anonymous, unrelated-user, owner, intended participant/group-member, and authorized-admin access, including direct object URLs, listing, uploads, overwrites, deletes and signed URL creation/expiry. Review how authorization is checked before issuing signed URLs. For verification documents require a private bucket and server-enforced least-privilege uploader/admin access before restoring the upload UI; the client's `createSignedUrl` call is not proof of authorization.
4. Design and review migrations only after the actual schema/policies are known. Plan a compatible transition from public URLs to authorized private delivery for existing and new media, handling existing links, access checks, rollback and availability. Do not simply flip a bucket or delete existing objects: that can break chats, lose access or leave exposed copies. Audit retained verification documents and existing public links through an approved incident-response/retention plan if exposure is confirmed; do not delete or move data without a separately approved plan and backups.
5. Validate policies and realtime/storage behavior with synthetic integration tests in staging, then review rollout and rollback with the project owner. Re-test production safely only with explicit authorization and test accounts. An independent design and cryptographic review is needed before offering end-to-end encryption; this branch does not attempt it.
