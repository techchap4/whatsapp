# Rada PWA

The existing install UI and push notification handlers remain in place. The manifest uses relative URLs, so serve this directory at `/` or a trailing-slash subdirectory such as `/rada/`. HTTPS is required in production (localhost is allowed for development). Serve `manifest.json`, `sw.js`, the SVG icons and PNG with their appropriate MIME types, and ensure the host serves `index.html` at the directory URL. The worker's default scope is its containing directory.

For privacy, the worker does not cache any requests or responses. Entry navigations use the network and show a generic, self-contained notice if the network fails; chats and calls do not work offline. API/auth/chat/media, other navigations and assets are not intercepted by the worker. This does not change normal browser HTTP caches or application storage. The old worker could have stored private responses in `rada-shell-v5` or other historical `rada-shell-v*` caches. The new worker neither reads nor deletes them: deleting caches automatically could remove user data. Users or administrators can review and clear those caches deliberately in browser storage settings. Other origin caches are left untouched. An existing old worker may handle requests until its update installs and activates; verify after deployment.

Run `node test-pwa.cjs` for network/offline routing and manifest checks. Test installation and updates in the target browsers and hosting environment before release; SVG icon support and install UI vary by browser. The existing web push setup requires its own server-side configuration. The repository references `whatsapp.css` and `whatsapp-inbox.js`, which were not present when this change was made; those pre-existing missing assets are not supplied by the PWA.

## Notification privacy and limitations

Message push payloads contain only the message type and sender routing ID, not message text, file names or sender names. The worker also displays generic text for legacy payloads and for calls; in-app background notifications are generic too. A routing ID is still present in message notification data and deep-link URLs. OS/app branding and notification history remain visible. No lock-screen privacy is claimed for an older worker, older backend function, or previously displayed notifications. Releasing the frontend alone does not update the existing Supabase Edge Function; deploy the reviewed function separately using the project's existing configuration. This PR makes no backend or deployment changes.

The message function checks the receiver's stored `profiles.settings.notif.messages` and `desktop` values and fails closed on lookup errors. Local per-chat mutes suppress message sounds and background notifications while the app is running, but are stored only in localStorage and are **not** enforced on closed-app push or other devices. The call-push implementation is not in this repository: call ringtone/vibration and background-alert settings are not reliably enforceable for closed-app pushes. Browser push `userVisibleOnly` behavior can also result in browser-generated alerts if a worker suppresses a push. These limitations must not be presented as complete muting. Calls retain their separate push path; subscriptions are not removed when changing these settings.

Notification clicks focus an app entry window and ask it to queue the chat until sign-in and profiles are ready. An older tab that does not acknowledge the request is navigated to the chat URL (which may discard an unsent draft); if no usable app window is available, a new one is opened. Manually test on installed and browser instances, with login, locked phone, multiple tabs, mute/settings changes and call delivery before release. Run `node test-notifications.cjs` for notification regression tests. With TypeScript available as a Node module, run `node test-push-function.cjs` for syntax/transpilation and mocked backend checks; alternatively set `TYPESCRIPT_MODULE` to the TypeScript module path. These tests do not contact a backend.
