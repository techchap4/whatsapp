# Rada PWA

The existing install UI and push notification handlers remain in place. The manifest uses relative URLs, so serve this directory at `/` or a trailing-slash subdirectory such as `/rada/`. HTTPS is required in production (localhost is allowed for development). Serve `manifest.json`, `sw.js`, the SVG icons and PNG with their appropriate MIME types, and ensure the host serves `index.html` at the directory URL. The worker's default scope is its containing directory.

For privacy, the worker does not cache any requests or responses. Entry navigations use the network and show a generic, self-contained notice if the network fails; chats and calls do not work offline. API/auth/chat/media, other navigations and assets are not intercepted by the worker. This does not change normal browser HTTP caches or application storage. The old worker could have stored private responses in `rada-shell-v5` or other historical `rada-shell-v*` caches. The new worker neither reads nor deletes them: deleting caches automatically could remove user data. Users or administrators can review and clear those caches deliberately in browser storage settings. Other origin caches are left untouched. An existing old worker may handle requests until its update installs and activates; verify after deployment.

Run `node test-pwa.cjs` for network/offline routing and manifest checks. Test installation and updates in the target browsers and hosting environment before release; SVG icon support and install UI vary by browser. The existing web push setup requires its own server-side configuration. The repository references `whatsapp.css` and `whatsapp-inbox.js`, which were not present when this change was made; those pre-existing missing assets are not supplied by the PWA.

## Draft notification changes — not ready to merge or deploy

**Do not merge or deploy.** This branch is incomplete and does not fix all notification privacy issues. The worker renders generic push notifications; the message-push function checks the recipient's stored message/background settings and omits content, names and avatars from its payload. It still transmits a sender routing ID, which may also appear in a new window's `?chat=` URL and browser history. Generic notifications still reveal the presence and type of activity.

Outstanding blockers and limitations:
- `app.js` direct message alerts still expose sender names, message previews and avatars; incoming call alerts expose caller names, avatars and call type. `extras.js` update/app alerts still expose their title and body. The direct call notification vibrates even if call vibration is disabled.
- The local mute is not checked by the current message listener even while the app is open. It is stored only in localStorage, so cannot suppress closed-app push or apply on other devices either.
- The existing menu does not handle the worker's `open-chat` message. For a focused existing app window, the worker now avoids navigation/reload to protect unsent drafts; until a safe client fix is applied, a click may focus the app without opening the chat. A new window is opened with a chat link only when no app window could be focused. Lookup/platform failures can still prevent reliable routing.
- `notification-client.patch` is **unapplied and unverified**, not a completed fix. Review it before use: its proposed listener calls `openChat`, while the current app has a shared message input and `openChat` changes the active recipient without clearing or associating that input with the original chat. Automatically switching chats can leave an unsent draft addressed to the wrong person. A safe fix must preserve drafts per chat or otherwise prevent wrong-recipient sends, and be tested.
- The separate call-push implementation is absent, so closed-app call content and settings cannot be fully checked or enforced here. The worker's call push vibration is unconditional. Browser `userVisibleOnly` policies may produce browser-generated alerts. Changing message settings does not remove push subscriptions.
- Older workers, deployed backend functions and previously displayed notifications remain unchanged. A frontend release alone does not update the Supabase Edge Function. Database policies, actual trigger configuration and settings persistence have not been verified against a live backend.

Run `node test-notifications.cjs` and `node test-pwa.cjs` for mocked worker and PWA checks. With TypeScript available as a Node module, run `node test-push-function.cjs` for transpilation and mocked backend checks; alternatively set `TYPESCRIPT_MODULE` to its module path. These tests do not cover the active client privacy defects or contact a backend. Real browser/device, installation, live backend, settings, calls, drafts and multi-window tests are required before release.
