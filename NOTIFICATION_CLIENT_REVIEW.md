# Draft client notification patch — DO NOT MERGE OR DEPLOY

This document, `notification-client-safe.patch` and `test-client-notifications.cjs` are review artifacts only. They do not apply the patch. The older `notification-client.patch` is unsafe: it changes the recipient while leaving the shared composer draft in place. Do not apply it. The safe patch was prepared against PR #2 head `ab114951d1283a248ead90dbfebcb2b621e006fa` and replaces, rather than builds on, the older proposal.

The patch makes in-page message, incoming-call and app/update browser notifications generic; suppresses message sound/alert while the sender is locally muted; checks message/background settings and browser permission and re-checks them, mute, visibility and account after asynchronous worker registration; and requests an empty vibration pattern for calls when the setting is off. OS/browser behavior can override notification/vibration behavior.

Notification clicks in an existing window focus it and show a draft-safety notice but deliberately **do not open or change the chat**. The existing shared composer is not per-recipient. A fresh shortcut window opens the target only when authenticated profile data is ready within 30 seconds and the user has not interacted, opened a chat or typed into the composer. Otherwise it remains in place. Browser restrictions, absent profiles, login/interaction or old clients can prevent routing. The ordinary existing app's manual chat switching still shares the composer and can misaddress an unsent draft; finish or clear a draft before changing chats. This is a separate release blocker, as are asynchronous send-failure and media workflows; this patch does not claim to fix them.

Closed-app mute remains impossible using localStorage alone. A server-side per-user/per-chat preference, enforcement in message/call dispatch and cross-device sync require backend changes and verification. Closed-app call push implementation is unavailable and its content and preferences cannot be verified; worker call vibration remains unconditional. Generic notifications still reveal activity and type. Message push still contains a sender routing ID and new-window URLs can expose it in browser history. Browser `userVisibleOnly` may generate alerts. Settings changes do not remove subscriptions. Previously delivered notifications and old workers are unchanged; frontend changes alone do not deploy the backend.

Local mocked checks: apply the safe patch to a clean copy of the exact PR head, then run `node test-client-notifications.cjs`, `node test-notifications.cjs`, `node test-pwa.cjs`, JavaScript syntax checks and `git diff --check`. The old worker test's warning about inactive client changes reflects the unchanged draft branch, not the locally patched copy. Tests do not verify production, real browsers, device permission behavior, multiple authenticated accounts, drafts during manual switching or real network/backend policy. Real device/browser, multi-window, manual draft/send/media, live database RLS, triggers, push delivery/settings and backend security tests are mandatory before any release.
